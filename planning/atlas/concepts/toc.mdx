## Show me

```text
book "MRK"
ChapterRow { start: 0,  end: 18,  token: MAX, number: 0 }              ← front matter is row 0
ChapterRow { start: 18, end: 125, token: 6, label 21..22, number: 1 }
VerseAnchor { at: 26,  chapter: 1, first: 1, last: 1, label 29..30 }
VerseAnchor { at: 63,  chapter: 1, first: 2, last: 3, label 66..69 }   ← "2-3"
```

```text
   0        0..18           0
```

## Why

- **Tokens, no tree.** `\c`, `\v` and their designators are flat facts, so an editor can hold a Toc without building a [[cst]]. 5.8 ns/token on en_ulb (commit 13c3d3b, when it replaced `ParseHeader`).
- **Rows tile `0..len`.** That makes `locate` total: every byte is in some chapter, and front matter is chapter 0, never a fabricated verse.
- **Labels and members are spans.** The spelling `12b` or `1,3,5` cannot be carried by numbers; positions are kept instead of copied text.
- **Degrade, never repair.** A malformed designator keeps its row with numbers 0, so the previous verse's extent cannot swallow it.
- **Structural extents.** A verse runs to the next `\v` or `\c`, so a heading before verse 4 sits in verse 3. [[resolve]]'s `opening` is the answer for a caller who wants the heading.

Trade-off: verse counts are the host's arithmetic. A bridge is one anchor naming several verses; the row carries both and picks neither.

## Composes with
