## The problem

Many questions are just "where": which verse is the cursor in, where does chapter 3 start, how many verses are in this book? Building the full document tree to answer them is wasted work on every keystroke. And every byte needs an answer, including the title page before chapter 1.

## The solution

We build a flat table straight from the scanned pieces: the book code, one row per chapter, and one entry per verse marker with its label. Chapter rows cover the whole file end to end, with the front matter as chapter 0, so "where is this byte?" always has an answer. Verse labels like `12b` or `1,3,5` are kept as positions into the file, because a pair of numbers cannot hold their spelling. This avoids the tree entirely, so an editor can keep a table of contents without paying for structure.

## Trade-offs

- A verse runs to the next verse or chapter marker, so a heading just before verse 4 counts as part of verse 3. [[resolve]] offers an "opening" point for callers who want the heading.
- A bridge like `\v 2-3` is one entry naming two verses. Counting verses is left to the caller.
- A malformed verse number keeps its row with numbers 0, rather than being guessed or dropped.

## Show me

The table for a 125-byte scratch book: front matter as chapter 0, then chapter 1 with three verse anchors, one of them a bridge.

```text
book "MRK"
ChapterRow { start: 0,  end: 18,  token: MAX, number: 0 }              ← front matter is row 0
ChapterRow { start: 18, end: 125, token: 6, label 21..22, number: 1 }
VerseAnchor { at: 26,  chapter: 1, first: 1, last: 1, label 29..30 }
VerseAnchor { at: 63,  chapter: 1, first: 2, last: 3, label 66..69 }   ← "2-3"
VerseAnchor { at: 113, chapter: 1, first: 4, last: 4, label 116..117 }
locate(10) = MRK chapter 0      locate(40) = MRK 1:1
```

`playground --toc-trace`:

```text
MRK — 2 chapter rows, 3 verse anchors, 125 bytes
  ch            bytes  verses  first anchors
   0        0..18           0
   1       18..125          3  MRK 1:1@26  MRK 1:2-3@63  MRK 1:4@113
```

## How it works

- **Tokens, no tree.** `\c`, `\v` and their designators are flat facts, read from [[token]] rows without a [[cst]]. 5.8 ns/token on en_ulb (commit 13c3d3b, when it replaced `ParseHeader`).
- **Rows tile `0..len`.** That makes `locate` total: front matter is chapter 0, never a fabricated verse.
- **Labels and members are spans**, read through the [[designator]] interpreter.
- **Degrade, never repair.** A malformed designator keeps its row with numbers 0, so the previous verse's extent cannot swallow it.

## Composes with

Reads [[token]] rows and the [[designator]] interpreter. Read by [[resolve]], [[vref]], [[diff]] (blocks are bytes between anchors), [[onion-book]], the [[pantry]] (pinned per book), the [[census]] wire and the [[dish]]'s `chapters`/`verses`/`members` sections.
