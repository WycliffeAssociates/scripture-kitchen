## The problem

An editor asks "show me Luke 1:2". In the file, verse 2 might be merged with verse 1 (`\v 1-2`), skipped (`\v 1,3`), or the whole chapter might appear twice by mistake. There may also be a heading just before the verse that the reader would want to see. The editor needs a byte range it can trust, or an honest "not here".

## The solution

We answer from the file's own table of verse positions ([[toc]]) with one of three results: found, missing, or ambiguous. Found carries the range to read, an earlier "opening" point that includes headings before the verse, and which verses it really covers. We never return the "nearest" match. Sefer's older code merged overlapping matches into one span, which silently hid broken text; that was not ported. The reference type itself lives in a shared crate, so any product can name a place in scripture without depending on the USFM engine.

## Trade-offs

- Answers are small JSON, not a compact binary format. That is fine for one answer per call on a slow path, but not for bulk lookups.
- Offsets are bytes unless the caller asks for UTF-16.
- A broken file gives "ambiguous" with every candidate, and the caller has to pick.

## Show me

Each line is a tiny source text, the reference asked for, and the answer. Note the bridge, the hole, the duplicate chapter, and the heading picked up by `opening`.

```text
\v 1-2 a b\n\v 3 c          LUK 1:2   → found \v 1-2 .. \v 3, covers LUK 1:1-2
\v 1,3 a\n\v 4 b            LUK 1:2   → missing verse within chapter 1
\c 3\n\p a\n\c 3\n\p b\n    LUK 3     → ambiguous [0..10, 10..20]
\v 3 a                      LUK 1:3a  → found \v 3, covers LUK 1:3, coarser
\v 1 a\n\s1 A heading\n\p\n\v 2   LUK 1:2 opening at \s1
```

At the JS wall:

```js
JSON.parse(resolve(text, { kind: "verses", from: { chapter: 1, verse: 2 }, to: { chapter: 1, verse: 2 } }));
//   { found: { from, to, opening, covers, coarser } } | { missing, within? } | { ambiguous: [...] }
```

## How it works

- **Every answer from the one text's [[toc]].** Ambiguity is malformed text, said so with every candidate in source order (`resolve.md`, "Where this departs").
- **`opening` is new.** `opening..to` is what a multibuffer clips: it walks back over line openers and headings before the first `\v`. `from..to` is what a check reads.
- **Members, not hulls.** A verse is found by the [[designator]]'s members, so `\v 1,3` does not claim verse 2.
- **Cases as data.** `testData/resolve/cases.json` holds cases any language can run (31 at first, commit 4b17b21); `gen_cases.py` reproduces it byte for byte (commit a28a2eb).
- **The Address type lives in [[mise]]**, so a place in scripture no text owns is not an onion type.

## Composes with

Reads the [[toc]] and the source (segment letters, the opening walk), using the [[designator]]'s members. Served by `onion-wasm`'s `resolve` and galley's `Galley.resolve`/`resolveOf` ([[galley-package]]); [[sefer]] is the asker.
