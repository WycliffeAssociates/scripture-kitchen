## The problem

Opening a project for the first time means parsing every book: 66 files for a Bible. Each parse already produces one buffer for JavaScript. Handing JavaScript 66 separate buffers means 66 crossings and 66 things to track. The caller also has its own names for the books (file paths, database ids) that the engine knows nothing about.

## The solution

The corpus envelope puts all the per-book buffers in one buffer. Each book's result is copied in unchanged, labelled with whatever name the caller gave it. Because the contents are not re-encoded, one reader decodes a single book and a whole project the same way. The engine never reads the labels, so they cannot disagree with what the caller meant. Books can be parsed in parallel before framing; the caller chooses how.

## Trade-offs

- A cold load does not fill the engine's per-book cache, so the first edit after it pays for parsing again. The file marks this as a TODO.
- Entries carry no checksum. Adding one is a format change: an entry is 16 bytes, and a 128-bit hash would add 16 more.
- Its JavaScript reader is written by hand, one of two wire formats that are not generated ([[wire]]).

## Show me

Two books framed together; look at the header, then one directory entry per book. From `galley/src/corpus.rs`:

```text
galley::corpus::plate(&[("GEN", gen_dish), ("EXO", exo_dish)])

bytes[0..4]    "ONCP"            magic
bytes[4..8]    1                 format version
bytes[8..12]   2                 book count
bytes[12..16]  0                 reserved
bytes[16..]    [keyAt, keyLen, dishAt, dishLen] x 2, then the bodies
```

## How it works

- **Frames, never re-encodes.** Each body is exactly what [[plate]] writes for one book.
- **Parallelism is the caller's.** Parsing is embarrassingly parallel per book: 28.80 ms on 10 threads against 158.38 ms serial for the English Bible.
- Not yet wired to the [[pantry]]: no chunk-cache seeding, no per-book checksum.
