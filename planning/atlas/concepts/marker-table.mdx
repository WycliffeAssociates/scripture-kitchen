## The problem

The scanner, walker, lint, mask and exports all ask the same per-marker questions (category, closing, legal contexts, deprecation), and the answers change when the spec does.

## The solution

One row per marker family, as named Rust fields. Codegen writes the packed lookup, the name matcher and the TypeScript table, all checked in and staleness-tested ([[invariants]] 6). A row index fits in a byte, so a [[token]] stores its marker as one `u8`, not a name ([[invariants]] 2).

## Trade-offs

- Behaviour is per row and fixed at build: a project can map a `\z` name onto a template row ([[extensions]]) but cannot redefine a spec marker.
- USFM 3.2 only. A 3.2 deprecation is a flag; there is no 3.1 column.
- Unknown markers, unregistered `\z` included, are row 0: bytes kept, no behaviour.

## Show me

Each token below carries the row number of its marker; the table tells you what that number means.

```usfm
\q1 \v 4 Bread.
```

```rust
tokens[q1].marker_idx == 95  // level 1; row "q": numbered UpTo, ParaPoetry
tokens[v].marker_idx == 133  // level 0; row "v": Verse point, payload Designator
tokens[s1].marker_idx == 110 // level 1
tokens[zfoo].marker_idx == 0 // row 0, the inert empty row, unless registered
```

Rows key on (canonical name, spelling shape): strip `-s`/`-e`, then digits. `q1..q4` are one row `q`; `qt3-s` is row `qt`.

```rust
// generated.rs: row 0 empty, rows 1..=152 spec markers, rows 153..169 the 17 template rows
static PACKED: [u128; 170] = [/* … */];
static NAMES: [&str; 170] = [/* … */];
pub const FIRST_EXTENSION_ROW: MarkerIdx = 153;
```

## How it works

- **One authored source, several generated projections.** Humans write named fields in `rows.rs`; codegen packs them into `u128` rows, a u64 name matcher (longest name is 6 bytes) and the `common_marker_checks` fast arms. The table stores facts, codegen turns facts into instructions, the lexer reads columns (`tables.rs` doc).
- **Referee is USFM 3.2 only.** 3.1's `usx.rng` is fallback evidence and never outvotes a 3.2 page. `deprecated` and [[code:onion/src/tables/schema.rs#AttrStatus::Deprecated]] record 3.2's own deprecations (`schema.rs`).
- **Derived facts are `const fn`s, not columns.** `precedence()` and context contribution are baked by codegen, so they cannot drift from the rows.
- **Unknown and unregistered `\z` markers resolve to row 0.** A registered one resolves to a template row ([[extensions]]).
- **The JS copy.** `onion-wasm/reader.ts` carries the generated `MARKERS` array (name, kind, category, closing, shape, numbering, whitespace rule) and `MARKER_ATTRIBUTES`, so `MARKERS[markerIdx]` is one array read.

## Composes with

The [[scanner]] stamps `marker_idx` from it. The [[walker]] reads scope columns. [[lint]], [[mask]] recipes and the [[exports]] read category and kind. The JS side gets the same table through generated code in `onion-wasm/reader.ts` ([[wire]]), including `MARKER_ATTRIBUTES`.
