## The problem

An editor, the CLI and Sous's adapter all need the same answers about a USFM book (where chapter 2 starts, what is malformed, the text without notes), the editor per keystroke. Separate parsers would disagree.

## The solution

One Rust engine every host calls. It never normalises on load, so every answer is an offset into the bytes the editor holds ([[invariants]] 1, 2), and it keeps nothing between calls, so caching is galley's ([[invariants]] 4). Native callers use [[onion]]; JS gets it through [[onion-wasm]] or the [[galley-package]].

## Trade-offs

- Stateless: each call re-reads the text it is given unless [[galley]] caches.
- Every fix comes back as edits for the host to apply, never a new file.
- USFM 3.2 in only; USJ, USX and HTML are exports, not inputs.

```ts
const { tree, tokens, diagnostics, toc } = deserialize(parse(text, { diagnostics: true, toc: true }));
```

## How it works

- **Source is the truth.** Every product is an index over or a derivation from the exact bytes ([[source]]); round trip is identity by construction.
- **One engine, many drivers.** The engine never forks per host (GLOSSARY, "Engine").
- **Stateless.** No stateful handle until a profiler shows the per-call index build matters (`onion-wasm/README.md`, "Deliberately absent").
- **Owns scripture structure for Sous** too: parsing, marker validity, canonical order, masks, verse anchors (`charter.md`). Sous does not grow a second USFM parser.

## Composes with

Built from the [[onion]] crate; the [[cst]] is its base. [[sous-chef]] reads it only through [[galley]]'s [[onion-book]].
