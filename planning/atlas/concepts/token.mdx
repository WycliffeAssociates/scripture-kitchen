## The problem

Once a file is cut into pieces, every later step reads those pieces: the tree builder, the verse table, the checks, and the editor in JavaScript. A long book has tens of thousands of them. If each piece were a rich object with copied text, memory and the cost of passing them to the editor would blow up.

## The solution

Each piece is a small fixed-size record (12 bytes in memory): where it starts, how long it is, what kind it is, which marker it is, and the marker's level (the `2` in `\q2`). It holds no text; the text is read from the file by position. Details inside a piece, like a verse number's value or a word's attributes, stay unread until someone asks ([[designator]], [[attributes]]). Every field we add has to be mirrored in the JavaScript reader too, so fields are added sparingly. Extra spaces between a marker and its content get their own kind, "Pad", so the editor can show them and the formatter can offer to delete them.

## Trade-offs

- Length is two bytes, so a piece is at most 65,535 bytes; longer text is split into several pieces. Why two bytes rather than four is not documented.
- Marker identity is one byte, so the [[marker-table]] can hold at most 256 rows.
- Readers that need a value inside a piece pay to interpret it each time.

## Show me

Eight pieces from one verse with a footnote. Each is a kind, its text (by position), and the marker row it points at.

```text
 11 Marker        "\v "          start=26 len=3  marker_idx=133
 12 Designator    "1 "           start=29 len=2
 13 Text          "Jesus wept."  start=31 len=11
 14 Marker        "\f "          start=42 len=3  marker_idx=21
 15 NoteCaller    "+ "           start=45 len=2
 16 Marker        "\ft "         start=47 len=4  marker_idx=32
 17 Text          "why"          start=51 len=3
 18 ClosingMarker "\f*"          start=54 len=3  marker_idx=21
```

Surplus delimiter whitespace becomes `Pad` (`scanner.rs` doc):

```text
\v 1 text    Marker("\v ") Designator("1 ") Text("text")
\v   1 text  Marker("\v ") Pad("  ") Designator("1 ") Text("text")
```

Whitespace inside text is never Pad: `\nd*   spoke.` lexes as `Text("   spoke.")`.

## How it works

- **Eager fields, lazy payloads.** `start: u32`, `len: u16`, `kind_bits: u8`, `marker_idx: u8`, `level: u8`. GLOSSARY: "each added field is twin tax", because the JS read lane must mirror it.
- **Packed kind.** The Rust enum is 2 bytes; the row stores one byte, low 4 bits shape and bit 4 a spelling flag (`\+` nesting, or `-e` on a milestone). `to_bits`/`from_bits` is the one mapping.
- **Pad** (RFC-Lexer-change-8-27, commit 8128053): each fold site keeps at most one horizontal code unit; the rest is Pad. Spans tile again, text views drop Pad whole, and `delimiter-surplus` (875 across the corpus at the time) offers a delete.
- **Level, not spelling.** `\q1` and `\q2` share one row; `level` carries the number.
- **Over-long runs split** at `u16::MAX` in the scanner's push.

## Composes with

Written by the [[scanner]] from the [[source]]. Read by the [[walker]] to build the [[cst]], by the [[toc]] without a tree, and by [[lint]]. Crosses in the [[dish]] as a 12-byte row (`start`, `end`, `kind`, `marker`, `level`, `flags`): `end` replaces `len` so every offset converts to UTF-16 in one sweep.
