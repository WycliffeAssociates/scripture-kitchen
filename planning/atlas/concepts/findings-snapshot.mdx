## The problem

Sous verdicts are corpus-relative: an edit in Mark can change a finding in Genesis. A host needs the complete current set after each publish, each finding at an exact place.

## The solution

A full snapshot, not a patch, because a distant edit can move totals anywhere. A finding is 16 bytes: start and end offsets, book index, kind code, flags and two kind-dependent numbers ([[invariants]] 2). Shared evidence (a pattern's counts) sits once in a pattern table that records point at. An array of JS objects would cost an allocation per finding.

## Trade-offs

- Every publish resends the whole set.
- Kind codes are dense; removing or renumbering one is a new wire version.
- A finding over removed markup publishes the outer source range, not pieces.

## Show me

One finding in "Jesus wept.", found in the cleaned text and published as a range in the raw file. Then the record layout. From `galley/src/sous/mod.rs` and `charter.md`:

## How it works

- **Fixed-width from day one** (`charter.md`): not a serialized Rust struct. Each code owns its two `i16` lanes; a `Convention` row names a pattern-table row instead of repeating its evidence.
- **Coordinates are composed in galley.** Sous emits projected-book UTF-8; galley maps it through the [[mask]] and [[utf16]] table to raw-book UTF-16.
- **Its own emitter.** The TypeScript reader is generated by sous-core, not [[ticket]], since sous-core must not depend on onion ([[wire]]).

## Composes with

Written by the [[expediter]] (resident) or `publish_onion_findings` (cold) from [[chapter-pass]] results placed through [[onion-book]]. Read through `sous-reader.ts`, shipped in the [[galley-package]].
