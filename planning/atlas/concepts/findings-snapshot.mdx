## The problem

Sous Chef flags things a reviewer should look at, like "this spelling occurs 1 of 1,053 times". Those verdicts compare each place against the whole project. So editing one chapter of Mark can change a finding in Genesis, because the totals moved. The editor needs the full, current list after each change, with each finding pinned to an exact spot in the file it shows.

## The solution

Each publication is a complete snapshot of every finding, not a list of changes. A finding is a 16-byte record: a start and end position, a book number, a kind code, flags and two small numbers whose meaning depends on the kind. Evidence shared by many findings, like a spelling pattern, sits once in a pattern table that records point to. Patches against the last snapshot were ruled out because a distant edit can shift totals anywhere. An array of JavaScript objects was ruled out in the charter from day one, in favour of fixed-size records.

## Trade-offs

- Every edit republishes the whole project's findings, even if one changed.
- The kind codes are dense with no gaps. Removing or renumbering one is a new wire version.
- A finding over removed markup (a footnote, say) publishes the outer range in the file, not exact pieces.
- The reader refuses anything it does not know (version, code, flag, bad range) rather than guessing.

## Show me

One finding in "Jesus wept.", found in the cleaned text and published as a range in the raw file. Then the record layout. From `galley/src/sous/mod.rs` and `charter.md`:

```text
publish_onion_findings([OnionInputBook::new("books/mrk.usfm", "\\id MRK\n\\c 1\n\\p\n\\v 1 Jesus \\f + \\ft note\\f* wept.\n")],
                       &[finding /* projected-book UTF-8: 0..13 over "Jesus  wept.\n" */], …)
  → SOUS corpus buffer, CoordinateSpace::Utf16
      directory  MRK  books/mrk.usfm  published_len 50  count 1
      record     from 21  to 50                        // raw-book UTF-16
```

```text
0..4 from u32 · 4..8 to u32 · 8..10 book_idx u16 · 10 code u8 · 11 flags u8 · 12..14 lane i16 · 14..16 lane i16
codes: 0 LengthProportionality · 1 Hygiene · 2 Convention · 3 SourceCopy · 4 Presence
```

## How it works

- **Fixed-width from day one** (`charter.md`): not a serialized Rust struct. Each code owns its two `i16` lanes; a `Convention` row names a pattern-table row instead of repeating its evidence.
- **Coordinates are composed in galley.** Sous emits projected-book UTF-8; galley maps it through the [[mask]] and [[utf16]] table to raw-book UTF-16.
- **Its own emitter.** The TypeScript reader is generated by sous-core, not [[ticket]], since sous-core must not depend on onion ([[wire]]).

## Composes with

Written by the [[expediter]] (resident) or `publish_onion_findings` (cold) from [[chapter-pass]] results placed through [[onion-book]]. Read through `sous-reader.ts`. [[sefer]] opens it via the [[galley-package]].
